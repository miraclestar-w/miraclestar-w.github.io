潜伏 16 年：SQLite WAL Bug 是如何被 TLA+ 揪出来的？dqlite 中招了吗？

2026-07-04 · SQLite, TLA+, 形式化验证, dqlite, WAL, Checkpoint, Bug 分析

潜伏 16 年：SQLite WAL Bug 是如何被 TLA+ 揪出来的？dqlite 中招了吗？

2026年6月25日，Canonical 的 dqlite 团队发布了一篇技术博客，揭示了如何使用形式化验证方法 TLA+ 发现一个潜伏在 SQLite 中长达 16 年的 bug。这个 bug 位于 Write Ahead Log (WAL) 的 checkpoint 机制中，可能导致数据库损坏。更关键的是，他们用同样的方法验证了 dqlite 并未受此影响。

一个藏了 16 年的 Bug

2025年3月，SQLite 发布了一个修复版本，解决了一个长期存在的 bug：在 Write Ahead Log (WAL) checkpoint 时，由于竞态条件可能导致数据库损坏。

这个 bug 最令人震惊的不是它的危害（实际影响很低），而是它已经在代码库中潜伏了 16 年——从 2010 年至今。更难的是，发现和复现这个 bug 都极其困难。

对于 dqlite 团队来说，还有一个更迫切的问题：dqlite 会受影响吗？

什么是 WAL 和 Checkpoint？

要理解这个 bug，得先搞懂 SQLite 的 WAL 模式。

WAL 模式的工作原理

SQLite 使用 WAL (Write Ahead Log) 模式来解决读写冲突：Writer 不会阻塞 Reader。

  • Writer 将数据写入一个特殊的暂存区——WAL 文件
  • Reader 可以忽略 WAL 中的新数据，直到数据稳定
  • 最终，暂存区的数据会被移动到主数据库文件——这个过程叫 Checkpoint

关键锁和共享内存

SQLite 用锁和共享内存来协调 WAL 的变化。我们只需要关心两把锁：

  • CKPT_LOCK（Checkpoint 锁）：防止多个 checkpoint 同时进行
  • WRITE_LOCK（写锁）：在向 WAL 追加新页之前获取

共享内存中有几个关键字段：

  • walSalt：WAL 每次重置时递增的计数器
  • mxFrame：WAL 的长度
  • nBackfill：已经 checkpoint 的页数，[nBackfill+1, mxFrame] 这部分还没复制到数据库

用 TLA+ 建模 Bug

要找出 bug 的确切触发序列，团队使用了 TLA+——一种形式化规约和验证语言。

建模思路

写 TLA+ 最难的部分是决定什么该建模，什么不该建模。目标是：

  • 最简单的 spec
  • 仍然忠实于现实
  • 能从中提取有用洞察

建模 WAL 和数据库

首先定义数据库和 WAL 的状态：

VARIABLE wal      \* WAL 中的页序列
VARIABLE db       \* 数据库中的页集合
VARIABLE nBackfill \* 已 checkpoint 的页数
VARIABLE mxFrame   \* WAL 长度
VARIABLE walSalt   \* WAL 重置计数器

初始化状态：

Init ≜
    ∧ wal = ⟨⟩
    ∧ db = {}
    ∧ nBackfill = 0
    ∧ mxFrame = 0
    ∧ walSalt = 0

建模 Append 操作

SQLite 向 WAL 追加页时，会先获取写锁。关键代码路径是 WalAppendTakeLock 和 WalAppend。

如果 WAL 已经全部 checkpoint（nBackfill = mxFrame），Writer 会重置 WAL：

∧ wal' = ⟨ frameNumber ⟩
∧ mxFrame' = 1
∧ nBackfill' = 0
∧ walSalt' = walSalt + 1

否则，就正常追加：

∧ wal' = Append(wal, frameNumber)
∧ mxFrame' = mxFrame + 1

建模 Checkpoint 操作

Checkpoint 的过程更复杂，因为要从共享内存读取数据，而这些数据可能在两次读取之间被 Writer 修改！

Checkpoint 分三步：

  1. CheckPointCopyHeader：复制 WAL 头部（mxFrame 和 walSalt）到局部变量
  2. StartCheckpoint：检查是否需要 checkpoint（nBackfill < safeMxFrame）
  3. Checkpoint：将 WAL 中的页移动到数据库，更新 nBackfill
Checkpoint ≜
    ∧ checkPointState = "waitingForLock"
    ∧ db' = db ∪ { wal[j] : j ∈ nBackfill+1‥Len(wal) }
    ∧ nBackfill' = safeMxFrame
    ∧ safeMxFrame' = 0
    ∧ checkPointState' = "notStarted"

复现 Bug：20 步见证数据丢失

定义了一个不变量 NoPageIsLost：数据库中不应有任何"空洞"——所有写入 WAL 的页都必须按顺序出现在数据库中。

运行模型检查器，仅 20 个状态就找到了一个反例！序列如下：

Bug 触发序列

关键竞态条件发生在：

  1. Checkpoint 开始时复制了 safeMxFrame = 2 和 pWalSalt = 0
  2. 在 checkpoint 执行期间，Writer 完成了一个追加并重置了 WAL（walSalt 从 0 变为 1，mxFrame 从 2 变为 1）
  3. Checkpoint 完成后，nBackfill 被设为 旧的 safeMxFrame (2)，但此时 mxFrame 已经是 1 了！
  4. 结果：nBackfill > mxFrame，导致页 2 从数据库中消失

这验证了 SQLite 官方报告中的 bug 描述。

dqlite 受影响吗？

dqlite 是 Canonical 开发的分布式 SQLite，需要与 Raft 共识算法协调写操作。关键差异：

  • dqlite 禁止用户发起的 checkpoint
  • dqlite 禁用自动 checkpoint
  • Checkpoint 时停止所有读写（stop-the-world）

建模 dqlite 的 Checkpoint

在 TLA+ 中，dqlite 的 checkpoint 需要先获取写锁：

DqliteCheckpointTakeLock ≜
    ∧ writeLock = "notTaken"
    ∧ writeLock' = "takenForCheckpoint"

通过扩展原有 spec，添加了获取和释放锁的动作。由于 Append 和 Checkpoint 都需要持有写锁，它们无法并发进行，从而消除了数据竞争。

模型检查结果

使用相同的不变量 NoPageIsLost 检查 dqlite 模型，没有发现任何错误！

结论：dqlite 不受这个 bug 影响。

SQLite 的修复方案

2026年3月5日，SQLite 披露了 bug 并发布了修复。修复方法很简单——在 checkpoint 时增加一个检查：

Checkpoint ≜
    ∧ checkPointState = "waitingForLock"
    ∧ IF walSalt = pWalSalt
       THEN
        ∧ db' = db ∪ { wal[j] : j ∈ nBackfill+1‥Len(wal) }
        ∧ nBackfill' = safeMxFrame
       ELSE
        ∧ UNCHANGED ⟨ nBackfill, db ⟩

如果 WAL 在 checkpoint 期间被重置（walSalt ≠ pWalSalt），就跳过这次 checkpoint。运行模型检查器确认，修复后不再触发不变量。

总结与思考

这个案例展示了 TLA+ 在工业级系统中的实际价值：

  1. 16 年的 bug 仅用 20 步复现——形式化验证的威力
  2. 竞态条件难以通过测试发现——并发 bug 需要数学方法
  3. dqlite 的额外锁设计意外地提供了保护——虽然不是为了这个 bug 加的
  4. 简单的修复方案——加一个 salt 检查就够了

对于使用 SQLite 或类似 WAL 机制的系统，这个案例提醒我们：并发控制的设计细节可能隐藏着长达数十年的隐患。
