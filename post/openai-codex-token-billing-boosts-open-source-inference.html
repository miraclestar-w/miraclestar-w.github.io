OpenAI砍了Codex按消息计费，开源推理引擎反而炸了

2026-07-21 · AI OpenAI Codex SGLang LLM推理

2026年4月2日，OpenAI把ChatGPT Plus、Pro、Business和Enterprise的Codex计费方式从"按消息"改成了"按token"。没有预告，没有过渡期，开发者一觉醒来发现账单逻辑全变了。

同一天，GitHub上SGLang的star数悄悄突破3万。这个由LMSYS非营利组织托管的开源LLM推理框架，已经在全球40万块GPU上跑着，每天生成万亿级token。

一个闭源巨头的计费调整，为什么恰好撞上了开源基础设施的爆发期？

消息计费时代的幻觉

在token计费之前，Codex的定价逻辑很简单：你发一条消息，它处理一次，算一次钱。Plus用户每月有固定消息额度，Pro用户额度更大。对轻度使用者来说，这种模式直观、可控。

问题出在重度场景。一个工程师用Codex做代码重构，一条消息可能触发数十轮上下文交互。按消息计费时，OpenAI收的是"对话次数"的钱；但实际消耗的计算资源是token。两套账本对不上。

更麻烦的是，按消息计费制造了一种虚假的成本预期。你以为花1美元能跑100次调用，结果每次调用内部吃掉了5000个token。到月底一看账单，额度早没了。

OpenAI的选择是：把定价权从"用户以为的消耗"拉回到"真实算力消耗"。token计费更精确，但也更透明——透明到让人 uncomfortable。

token计费之后，谁在受益

按token计费之后，开发者的成本结构发生了微妙变化。

短对话变贵了。长对话里，输入token被缓存命中后，重复部分不再计费。这意味着高频复用prompt的工程场景反而省钱。CI/CD流水线、自动化测试、批量代码审查——这些场景突然变得经济可行。

而这类场景，恰恰是开源推理引擎的主场。

vLLM、SGLang、TensorRT-LLM这些框架的核心价值不是"更快生成一段文字"，而是"让大规模、高并发的推理请求变得便宜"。当OpenAI把Codex的成本结构暴露给开发者时，很多人开始算一笔账：我自己部署推理服务，真的比用API贵吗？

答案取决于规模。日调用量超过一定阈值后，自部署的边际成本远低于API。而这个阈值，在token计费之后变得更低了。

SGLang的40万GPU是怎么来的

SGLang的故事不是从"开源替代闭源"开始的。它从一开始就是一个性能问题驱动的项目。

LMSYS（Large Model System Organization）是一个专注于大模型系统的非营利研究组织。他们发现，现有推理框架在prefix caching、continuous batching、speculative decoding这些关键优化上各自为战，没有一个框架能把它们串起来。

SGLang的核心创新是RadixAttention——一种基于前缀树的KV cache复用机制。传统方案要么完全重算，要么缓存所有历史token。RadixAttention把相同前缀的KV cache组织成树形结构，命中时直接复用，未命中时增量计算。

这不是理论优化。在Llama 3.1 70B的基准测试中，RadixAttention让前缀缓存的命中率从30%提升到80%以上。对于多轮对话、批量代码生成这类高频复用prompt的场景，延迟直接砍半。

40万GPU的部署规模不是营销数字。xAI、AMD、NVIDIA、LinkedIn、Cursor、Oracle Cloud、Google Cloud、Microsoft Azure、AWS都在用它。MIT、UCLA、Stanford、UC Berkeley、清华大学也在用。

这个数字意味着什么？意味着全球相当一部分LLM推理流量，跑的其实是开源代码。

开源推理引擎的暗线竞争

SGLang、vLLM、TensorRT-LLM、TGI——这四个名字构成了2026年LLM推理引擎的基本盘。它们之间的竞争不是"谁更好"，而是"谁的架构更适合你的场景"。

vLLM的优势在于PagedAttention和广泛的模型支持。它是第一个把操作系统内存分页思想引入KV cache管理的框架，概念简洁，工程成熟。很多生产环境的首选。

TensorRT-LLM的优势在于NVIDIA生态的深度整合。如果你用的是A100/H100/GB200，TensorRT-LLM能提供最低的延迟和最高的吞吐。但代价是学习曲线陡峭，定制成本高。

TGI（Text Generation Inference）是Hugging Face的官方推理服务。它的优势在于与Hugging Face模型生态无缝对接，适合快速原型和中小规模部署。

SGLang的独特之处在于，它在RadixAttention的基础上，把prefill-decode分离、speculative decoding、multi-LoRA batching、chunked prefill这些高级特性全部整合到一个统一调度器里。它不是单一优化，而是一个完整的推理runtime设计。

这种设计哲学让它特别适合复杂的多Agent场景——多个Agent同时发起推理请求，每个请求的prompt都有重叠前缀，RadixAttention能最大化缓存命中率。

而这，恰好是OpenAI Codex计费改革后，开发者最关心的场景。

计费改革背后的信号

OpenAI把Codex改成token计费，表面上是定价策略调整。深层看，这是一个信号：闭源API的成本结构正在被开源基础设施重新定义。

当开发者发现自己用API的成本可以精确到每个token，他们会开始对比：这个token如果在我自己的GPU上跑，成本是多少？

答案是：取决于GPU类型、模型大小、并发量、缓存命中率。但对于大规模部署，自部署推理服务的单位成本可以比API低一个数量级。

这不是"开源打败闭源"的叙事。这是"成本透明度改变用户行为"的叙事。

OpenAI可能没想到，token计费会让这么多开发者去研究SGLang和vLLM。它原本只是想让自己的定价更准确，结果意外地给开源推理引擎做了一次免费的市场教育。

接下来会怎样

2026年下半年，LLM推理引擎的竞争会从"单点性能"转向"整体调度"。

SGLang v0.5已经引入了DFlash和Spec V2，进一步提升了speculative decoding的效率。vLLM的Model Runner V2也在追赶。TensorRT-LLM在GB300 NVL72上实现了25倍推理性能提升。

但真正的变量不在这些框架本身，而在硬件层面。NVIDIA的Blackwell架构、AMD的MI355、Google的TPU v5e——每一代新硬件都会重新定义推理成本的下限。

当硬件成本持续下降，开源推理引擎的自部署经济性会越来越好。OpenAI的token计费改革，只是把这个趋势提前暴露给了更多开发者。

最后说个细节。SGLang的Slack频道里，有一个#pricing-calculator的讨论串。里面有人在算：用SGLang + A100自建推理服务，对比OpenAI API，日调用量多少以上开始省钱。

最高赞的回答只有一行："取决于你的缓存命中率。"
