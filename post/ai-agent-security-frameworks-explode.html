AI Agent 安全框架炸了：GitHub 上 10 万星的项目突然都在谈安全

2026-07-13 · AI, Agent安全, eBPF, SemaMesh, ClawShield

2026年7月，GitHub Trending 上最炸裂的现象不是某个大模型，也不是某个编程语言的新版本——而是整整一批 AI Agent 安全框架同时冲上热门。

mattpocock/skills 16万星，单日增长1712。obra/superpowers 25万星，单日增长1013。addyosmani/agent-skills 7.6万星，单日增长1116。这些项目有一个共同点：它们都在解决同一个问题——AI Agent 到底能做什么、不能做什么。

但真正有意思的不是这些框架本身，而是围绕它们的争论。有人觉得 Agent 应该拥有自由探索的能力，有人觉得每个 Agent 都应该被关在笼子里。这场争论正在重塑整个 AI 基础设施的走向。

从"能跑就行"到"不能乱跑"

去年这个时候，GitHub 上的 AI Agent 项目几乎清一色在讨论怎么让 Agent 更聪明、更自主。写代码、调 API、做决策——越自由越好。开发者们忙着给 Agent 加工具、加记忆、加推理能力，没人关心 Agent 会不会把生产数据库的密码发到公开的 LLM API 上。

今年变了。

SemaMesh 这个项目描述里只有一句话："sidecarless service mesh designed specifically for the era of autonomous AI agents"。它不关心 Agent 有多聪明，只关心 Agent 会不会把生产数据库的密码发到公开的 LLM API 上。这个项目的核心功能很简单——它拦截 K8s 集群里所有微服务对 OpenAI、Anthropic、Gemini 等外部 LLM 提供商的请求，记录谁发的、发了什么、花了多少钱。它甚至能做 PII 脱敏，在数据离开集群之前自动 scrub 掉敏感信息。

ClawShield 更直接——它就是一个安全代理，拦截所有发给 LLM 的消息，扫描提示词注入、PII 泄露、密钥外泄。它的架构图画了三层：Go 代理、iptables 防火墙、eBPF 内核监控。三层独立运行，任何一层检测到威胁都会触发跨层自适应响应。比如 eBPF 检测到提权行为，代理层会自动把注入检测灵敏度调到最高五分钟；代理层发现 60 秒内拦截了 3 次注入攻击，整个系统会强制进入 deny-by-default 模式十五分钟。

Raypher-core 走得更远。它把 Agent 的身份绑定到 TPM 芯片上，用硬件级加密锁死 Agent 的运行环境。Agent 换了机器就瘫痪。它的信任评分系统从 0 到 1000，低于 500 分的 Agent 只能读不能写，高于 900 分的才能完全自主执行。它还内置了 Fleet Management 功能——CISO 可以一键向 10000 个端点推送策略，2 秒内生效。

这不是巧合。当 AI Agent 开始接触真实的生产环境，安全问题从"锦上添花"变成了"生死攸关"。

eBPF 成了安全框架的新标配

有意思的是，这批安全框架几乎都用到了 eBPF。

SemaMesh 的 v0.6.0 路线图里明确写了 "eBPF Transparent Redirection"，目标是消除应用 URL 修改的需求。ClawShield 的内核监控层直接追踪 execve、tcp_v4_connect、openat2、setuid 这些系统调用。Raypher-core 在 Linux 上挂载 eBPF XDP 和 KProbes 到内核 tracepoint。

eBPF 为什么成了安全框架的首选？因为它能看到一切，而且不需要改应用代码。

传统的安全方案要么在应用层加 SDK（开发者要改代码），要么在网络层做流量镜像（看不到进程内部行为）。eBPF 介于两者之间——它在内核里运行，能看到每个进程的 syscall，但又不需要修改任何用户态代码。这意味着你可以给一个跑了三年的老服务加上实时安全监控，不用重启，不用改一行代码。

对于 AI Agent 这种需要深度观察的应用场景，eBPF 几乎是唯一可行的方案。Agent 的行为是非确定性的，传统的基于规则的安全策略根本跟不上它的变化节奏。只有在内核层面实时监控每一个系统调用，才能真正理解一个 Agent 在干什么。

安全框架的架构分歧

虽然大家都在做 Agent 安全，但思路差异很大。

SemaMesh 走的是"可观测性优先"路线。它不主动拦截流量，而是记录每一个 LLM 请求的详细信息——谁发的、发了什么、花了多少钱、用了哪个模型。它的审计日志是结构化 NDJSON 格式，可以直接喂给 SIEM 系统做合规分析。Prometheus 指标暴露了 token 用量、估算成本和 HTTP 状态码。它的 Grafana 仪表盘能实时展示每个命名空间的 AI 支出，这在 FinOps 场景下特别有用。

ClawShield 走的是"拦截优先"路线。它的默认策略是 deny-by-default，每条消息都要经过四个扫描器（提示词注入、PII、漏洞扫描、恶意软件）才能放行。它甚至内置了五个带 RAG 知识库的 AI Agent 来做辅助分析——Anvil 负责软件开发分析，Shield 负责安全工程评估，Harbor 处理云工程问题，Beacon 管危机沟通，Lens 做情报分析。

Raypher 走的是"身份绑定"路线。它的核心创新是把 Agent 的身份锚定到硬件上，而不是软件配置。Agent 换一台机器就失效，API Key 用 TPM 密封，即使被偷也解不开。它的零接触 MITM 功能还能终止 TLS、检查 payload，自动拦截信用卡号、社保号和 AWS 密钥。

这三种思路各有优劣。可观测性好但防护弱，拦截强但误报多，身份绑定了但部署复杂。目前还没有一个方案能同时做到这三件事。

开源社区的分裂

GitHub 上的争论也很真实。

在 mattpocock/skills 的 Issue 区，有人提出一个尖锐的问题："如果 Agent Skills 可以访问文件系统，那它们能不能访问网络？"这个问题引发了超过 200 条评论。支持者认为 Agent 应该有完整的系统访问权限，否则就是"阉割版 AI"。反对者则认为，没有沙箱的 Agent 就是定时炸弹。

obra/superpowers 的 README 里直接写了一句："The agent checks for relevant skills before any task. Mandatory workflows, not suggestions."这句话被不少人解读为"把 Agent 当员工管"，也有人说是"工程化的必然结果"。

ClawShield 的作者在博客里写了一段话，后来被转载了很多次："Treating an autonomous, non-deterministic agent like a trusted human user is a catastrophic security vulnerability. A hallucinating—or hijacked—agent is effectively local remote code execution."

这段话翻译成大白话就是：你不能用信任人类的方式去信任一个会幻觉的 Agent。一个被劫持的 Agent 跟本地远程代码执行没什么区别。

下一步是什么

这批安全框架大多还在早期阶段。SemaMesh 刚出 Alpha，ClawShield 的 prod 实例只有一个域名，Raypher-core 才 1 个 star。但它们的方向很清晰——AI Agent 的基础设施正在从"功能驱动"转向"安全驱动"。

未来半年，我们可能会看到更多类似的项目出现。eBPF + AI Agent 安全这个组合，大概率会成为 K8s 生态的下一个热点。

至于那些还在讨论"Agent 该不该有自由"的人，也许该看看现实了——当 Agent 开始接触真实数据的时候，自由和安全从来不是二选一，而是先活下来再谈自由。
