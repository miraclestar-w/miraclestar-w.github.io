Cloudflare 密码学库翻车：AI 挖出 7 个漏洞，1 行代码就能修

2026-07-08 · Cloudflare CIRCL AI审计 密码学 漏洞挖掘 zkSecurity

Cloudflare 旗下 CIRCL 密码学库上线几个月后，zkSecurity 团队把他们的 AI 审计管道对准了这个库。AI 挖出了 7 个真实漏洞，全部已修复。其中最致命的一个——CP-ABE 访问控制完全失效——只需要一行代码的改动就能修好。

这不是什么理论上的安全问题。这些漏洞影响的是实际部署中的加密通信、身份认证和密钥共享。

一个"聪明"的 bug

第 7 号漏洞是 zkSecurity 自己的 AI 审计工具 zkao 独立发现的。它在 CIRCL 的 CP-ABE（密文策略属性基加密）实现里找到了一个逻辑错误。

CP-ABE 是一种高级加密方案，允许你这样写加密策略："(位置在美国 AND 部门是财务) OR (角色是管理员)"。只有满足策略的用户才能解密。听起来很美好。

但 zkao 发现，AND 门（"与"逻辑）的实现有问题。AND 门应该把一个秘密分成两份，每一份单独都无法恢复原始秘密，必须两份合起来才行。这是 AND 门的定义。

然而代码里，其中一个子节点得到的值是 0，另一个得到的是完整的秘密。这意味着只需要一个子节点就能恢复整个秘密。AND 门变成了 OR 门。

更糟的是，为了让系统达到 CCA 安全（抗选择明文攻击），tkn20 实现会在每个策略外面再套一层 AND 门。这层外层 AND 门的左子节点是一个"通配符"叶子——每个密钥都天然满足这个条件。

把这两件事放在一起：通配符叶子恰好是外层 AND 门的第一个子节点（In0），而 In0 又恰好是那个拿到完整秘密的子节点。

结果就是：每个密钥都能独立解密，不管策略怎么写的。访问控制完全失效。

修复方法是一行代码：

// 修复前：In1 被设为 0
shares[gate.In1] = newMatrixZp(k.rows, k.cols)  // In1 = 0

// 修复后：In1 = parent - In0
shares[gate.In1].sub(shares[gate.Out], shares[gate.In0])

浮点数精度丢失

第 1 号漏洞发生在阈值 RSA 签名（TSS/RSA）的多项式求值中。

阈值签名把秘密密钥分成 n 份，分给 n 个参与者。每个参与者的份额通过对秘密多项式求值得到。代码里，系数是 big.Int（大整数），没问题。但计算 x^i 的时候用了 float64：

xi := int64(math.Pow(float64(x), float64(i)))

float64 只有 53 位尾数。当 x^i 超过 2^53（约 9×10^15）时，结果会被静默舍入，然后再转回整数。

举个例子：100 个参与者、阈值 27 的情况下，在 x=100、i=26 处求值，需要计算 100^26 = 10^52。这比 2^53 大了 36 个数量级。即使 x=20、i=16 就已经出错了。

后果是多项式被错误求值，分发给参与者的密钥份额本身就是错的。签名组合要么直接失败，要么产生看起来正确但无法重构预期密钥的份额。

AI 把这个标为"严重"，Cloudflare 确认后的评级是"低"——因为触发条件在实际中不太可能出现。但一旦触发，问题确实存在。

修复方法是把浮点指数运算替换为 Horner 方法的多项式求值，全程使用 big.Int。代码里原来的 TODO 注释早就暗示了这一点。

一个只值 1 比特的证明

第 2 号漏洞在 zk/qndleq 模块，这是一个 DLEQ（离散对数相等）证明系统，用于证明两对值拥有相同的离散对数。

问题的核心在于安全参数 SecParam。这个参数决定了证明挑战的比特长度。正常情况下，验证者应该自己设定这个值。但代码里，SecParam 放在了 Proof 结构体本身里面：

type Proof struct {
    Z, C     *big.Int
    SecParam uint
}

验证过程中，代码用证明自身的 SecParam 来重新计算挑战。而这个字段是攻击者可控制的。

设 SecParam = 1，挑战坍缩成 1 比特（0 或 1）——每次伪造尝试相当于抛硬币。设 SecParam = 8，暴力破解大约需要 256 次尝试。无论哪种情况，证明系统的可靠性都没了。

这是一个反复出现的模式的典型案例：安全参数必须由验证者固定，却从证明者提供的数据中读取。

语言级别的陷阱

第 5 号漏洞几乎就是一个 Go 语言层面的陷阱。

在 HPKE 的 verifyPSKInputs 函数里，switch 语句的 case 标签用了位或运算符：

case modePSK | modeAuthPSK:  // 0x01 | 0x03 == 0x03，即只有 modeAuthPSK

在 Go 中，case a | b: 是一个单一 case，其值为两个常数的 OR，而不是两个 case。所以 case modePSK | modeAuthPSK 实际上是 case 0x03，而 modePSK（0x01）根本不匹配任何 case。

本该拒绝缺少 PSK 的分支被跳过了。

效果是：SetupPSK(..., nil, nil) 带着空 PSK 继续执行，而不是被拒绝。PSK 模式本应要求 PSK 材料；这里静默地丢弃了认证前提条件，让部署运行在一个比配置更弱的模式下。

修复方法是从 OR 改为逗号分隔的 case（case modePSK, modeAuthPSK:）。一个字符的改动。

AI 的盲点

最有意思的发现之一是 AI 对自身发现的严重程度评估非常不准确。

7 个漏洞中，AI 高估了 5 个的严重性，低估了 1 个（第 3 号 BLS 聚合验证漏洞），还有 1 个评估合理。

第 3 号漏洞尤其值得注意。AI 把它标为"中等"，但实际上这是一个经典的 rogue key 攻击——在密码学界属于教科书级别的高危漏洞。Cloudflare 确认为"高"。

AI 的推理过程显示，它正确识别了缺失的消息唯一性检查，甚至命名了 rogue key 攻击。但它锚定在"BASIC 模式的契约把唯一性要求放在调用方身上"这个事实上，把它当作缓解措施，降低了严重性评级。

我们不知道为什么会这样。这可能真的很难——当目标是像 CIRCL 这样被许多不同应用使用的库时，影响取决于下游调用者，而模型看不到这些信息。

模型配对不是对称的

另一个有趣的发现：模型配对的效果不是稳定的。

6 个漏洞中有 5 个是由 Claude Opus 4.6 配合他们的 skills 发现的。GPT-5.3 主要在做验证而非发现——除了第 5 号 HPKE 漏洞。

但几周后，他们换成了 Opus 4.7 和 GPT-5.4，角色基本反转了：GPT-5.4 发现了更多漏洞，Opus 4.7 只能做验证。

这提醒我们不要对特定模型名称过度拟合结论。前沿技术在不断移动。

不只是 Cloudflare

zkSecurity 扫描了 200 多个密码学项目（从下载量最高的加密 crate/package 中选择），产生了超过 1000 个候选发现。最大的瓶颈现在是 triage（分类）——每个报告的漏洞都需要专家检查技术有效性才能提交给项目方。

他们讨厌 AI spam，正如所有人一样。

这篇文章是系列的第一篇。他们计划继续发布来自其他项目的已确认漏洞。

如果你维护一个密码学项目，他们表示愿意一起验证——在 serious bugs 被修复之前找到它们。

写在最后

CIRCL 的维护者们响应很快，所有报告的漏洞都在短时间内修复了。

但真正值得思考的不是这些 bug 本身，而是这个过程揭示的东西：AI 能在密码学代码中找到真实漏洞，但它对严重性的判断不可靠，它不会把分散的观察串联成更有影响力的利用链，而且它的表现会随着模型版本的更替而波动。

"Every reported bug has to be checked by our experts for technical validity before it reaches a project, because we hate AI spam as much as everyone else does."

AI 能发现问题。但信任worthy的报告仍然需要人来把关。至少在目前是这样。
